# 【F006】合約下載 — 資料來源變更（原編號 F005-2，2026-07-13 更正編號，見 `00_主需求.md`）

> 資料源頭改變的歷史。持續累加，不覆蓋舊紀錄。

## 2026-07-13

直接核對本機 DB（`kenda_dealer` 表）發現：**49 筆經銷商裡有 47 筆 `country` 欄位是空的**，只有 2 筆填了 `TW`；`import-data/upsert_import.py` 目前也完全沒有處理 country 欄位的匯入邏輯。F005-2 前台「依國家＋胎種別自動篩選」的邏輯若照現有資料跑，幾乎篩不出任何合約。

**需要跟建大要新版經銷商清單（含國家欄位）**，比照之前分類欄位那次的處理模式（見 [[kenda-category-logic-doc]]）：
1. 建大提供新版經銷商 Excel（含國家欄位）
2. 改 `upsert_import.py` 加入 country 欄位對照
3. 重跑本機 DB upsert（non-destructive）
4. 驗證後推送遠端 aiuptop.com

胎種別欄位（`kenda_dealer_category_rel`）覆蓋率沒問題（48/49），不受此次資料來源變更影響。

## 2026-07-13（後續，同日）— 改用既有資料換算，不用等建大新 Excel

Jenny 指示：客戶主檔（`下單平台資料交換-202612.xlsx` / `excel_data_new.json`，即目前匯入用的來源檔）D 欄「區域別代號(regionCode)」可對應**集團代號檔 B 欄「代號(code)」（限 代號類別=CD 區域別）**換算出國家，不用等建大另外提供新 Excel。

- 核對後現行客戶主檔 46 筆經銷商，`regionCode` **全部是 `NMR`**（= 集團代號檔裡「台灣地區」），換算後全部是 `TW`
- 集團代號檔另外還有 31 筆 CD 區域別代號，其中可清楚收斂成單一國家的：`D01-D05`(TAIWAN)→TW、`C01-C08`+`JJJ/SSS/TTT/UUU`(CHINA)→CN、`V01-V03`+`VVV`(VIETNAM)→VN、`I01`+`III`(印尼)→ID、`F08`(INGLAND)→GB；`AAA`(美加)/`BBB`(中南美)/`CCC`(亞洲)/`DDD`(中東非洲)/`EEE`(歐洲)/`GGG`(紐澳) 這 6 個是跨多國的大區代號，無法收斂成單一國家碼，**暫不填**，等未來真的有這些地區的經銷商上線再另外處理
- 對照表寫在 `import-data/upsert_import.py` 的 `REGION_COUNTRY` dict，`kenda_dealer.py` 的 `country` 欄位 help text 也同步更新，不再寫「需建大提供」

**已在本機執行 upsert 並驗證**：46 筆經銷商中 43 筆成功寫入 `country='TW'`。另外 3 筆（`M01011`／`R02019`／`R03233`）在核對時發現各自有**重複的 dealer 記錄**（同 customer_code+company_code 出現兩筆，違反 model 宣告的 unique constraint，但 DB 上這條 constraint 顯然沒有真的生效），舊資料沒有清過，upsert 的 `search(limit=1)` 只更新了其中一筆，另一筆仍是空的——這是既有資料品質問題，不是這次改動造成的，寫在 `05_問題追蹤.md`，先不擅自合併/刪除。

**尚未推送到遠端 aiuptop.com**，目前只在本機驗證。
