# 【F006】合約下載 — 問題追蹤（原編號 F005-2，2026-07-13 更正編號，見 `00_主需求.md`）

> 開發／測試過程中發現、尚未解決或待使用者決策的問題。每則標日期，狀態用 待確認／待修／已解決／不處理。

## 2026-07-13

**問題**：`kenda_dealer.country` 欄位 49 筆裡 47 筆空值，前台「依國家＋胎種別自動篩選」在拿到新資料前無法正確運作（篩選結果會是空的或不準）。
**狀態**：已解決 —— 改用客戶主檔 regionCode 對照集團代號檔換算，不用等建大新 Excel，本機已 upsert（詳見 `03_資料來源變更.md` 2026-07-13 後續紀錄）。43 筆單一 dealer 記錄的經銷商已正確補上 `TW`；另外 3 筆因下面的「重複 dealer 記錄」問題只補到其中一筆，仍待處理。尚未推送遠端。

## 2026-07-13（同日，第二則）

**問題**：驗證 country 補值結果時發現 `M01011`（弘暘）／`R02019`（正鴻）／`R03233`（艾奇美）這 3 個客戶代號，`kenda_dealer` 表裡**各自有兩筆重複記錄**（customer_code + company_code 完全相同），違反 model 宣告的 `customer_code_company_uniq` unique constraint，但 DB 上這條 constraint 顯然沒有真的生效（可能是欄位/約束是在髒資料已存在之後才加上，migration 沒有清過舊資料就沒真的建立成功）。upsert 腳本用 `search(..., limit=1)` 只會更新其中一筆，另一筆維持原樣（這次是country留空）。
**狀態**：已解決（2026-07-14）—— Jenny 決策：刪除沒有訂單/報價/地點等資料的那一筆空殼記錄；正鴻（R02019）那組因為兩筆都有資料，先把少量資料（1筆訂單/1筆報價/1個地點）轉移到資料量較多的那筆，再刪除空的那筆。本機＋遠端都已執行：
- 弘暘 M01011：本機保留 id=58（51訂單），刪 id=103（空殼）；遠端保留 id=5（51訂單），刪 id=51（空殼）
- 正鴻 R02019：本機保留 id=77（轉入後35訂單/6報價/9地點），刪 id=102；遠端保留 id=6（轉入後70訂單/8報價/9地點），刪 id=50
- 艾奇美 R03233：本機保留 id=96（24訂單），刪 id=104（空殼）；遠端保留 id=4（24訂單），刪 id=52（空殼）

本機＋遠端經銷商總數都從 49 筆降為 46 筆，`customer_code` 不再重複。unique constraint 沒有另外處理（既有重複已清乾淨，之後 upsert 不會再產生新的重複，暫不需要）。
