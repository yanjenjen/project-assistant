## 2026-07-16 — 用真實合約書測試時發現：中文檔名下載會壞掉（已修復）

**狀態**：已解決，本機＋遠端都已修復並驗證

用 Jenny 提供的12份真實合約書（`0714測試用附件\店招合約書下載_功能範本\合約書`，原始為.doc/.DOC/.docx/.XLS，已用Word/Excel COM自動化轉成PDF）灌進 `kenda.contract` 測試時發現：`GET /contracts/<id>/download` 只要檔名含中文（`file_name`／`title` 是中文，例如「KD PCR一般店.pdf」），下載請求會直接連線逾時，不會回傳正常錯誤。

**根因**：`controllers/content.py` 的 `Content-Disposition: attachment; filename="{filename}"` header 直接把中文檔名塞進 HTTP header，但 HTTP header 只能用 latin-1 編碼，werkzeug 送出 response 時對中文字元編碼失敗（`UnicodeEncodeError`），導致連線掛住逾時而非正常回傳錯誤訊息——這個 bug 從 F006 一開始開發就存在，先前的技術驗證用的demo資料檔名剛好沒觸發，這次用真實中文檔名才第一次暴露。

**修復**：`content.py` 改用 RFC 6266 雙重格式——ASCII fallback（`filename="..."`，非ASCII字元被過濾掉）+ `filename*=UTF-8''...`（真正的中文檔名，percent-encoded）。本機測試（R02012帳號，D16/AC）下載 id=7（KD PCR一般店）驗證通過：HTTP 200、正確PDF bytes、header正確帶雙重檔名格式。已同步部署到遠端（`content.py` 備份為 `.bak_20260716b`，restart odoo-server）。

**測試資料**：12份真實合約書已灌進本機+遠端 `kenda.contract`（依廠別對照集團公司定義表換算原產國：KD/KF→D16台灣，KC/KS/KT→D14中國，KI→D08印尼；胎種別PCR一律對應現行代碼AC；廠別欄位因model只有建大(1)/建豐(F)兩選項，只有KD/KF填得進去，其餘廠別留空）。

## 2026-07-16（第二則）— Jenny 實測發現：廠別沒有真的擋前台可見性（已修復，真bug非誤解）

**狀態**：已解決，本機+遠端都已修復並驗證

Jenny 用正鴻（R02019，`company_code='F'`即建豐台灣）登入前台，發現「合約下載」清單除了2份建豐(KF)的合約，還多顯示了1份**建大(KD)**的合約「KD PCR一般店」——不合理，建豐的經銷商不該看到建大的合約。

**根因**：`_contract_visible()`（`controllers/content.py`）本來只比對 `country` + `category_ids`，完全沒比對 `factory`。`kenda_contract.py` 的 `factory` 欄位原本的 help text 寫「前台不顯示，僅供後台維護與比對」，這句話對了一半、錯了一半——`factory` 確實不會顯示成前台的欄位/直欄，但**應該要用來決定該合約前台可不可見**，這是2026-07-13設計討論時遺漏的邏輯，不是「各廠商企只能維護自己廠資料」那個已經明確決定延後的**後台維護權限**（見 `kenda_permission_control_backlog.md`）——兩者是不同的兩件事：這次修的是「經銷商只能看到自己廠別的合約」（前台可見性過濾，PPT Slide 6 原文有明確舉 R02019 這個例子當範例），不是「哪個內部員工能編輯哪個廠的合約資料」（後台維護權限，仍然照原計畫延後）。

**修復**：`_contract_visible()` 加一段 `factory` 比對（`rec.factory` 與 `dealer.company_code` 不同則不可見，留空＝不限，邏輯跟既有的country/category_ids比對一致）；同步修正 `kenda_contract.py` 的 help text 講清楚「留空＝不限廠別；比對經銷商自己的廠別決定前台是否可見；不會顯示成前台欄位」，避免以後又被誤讀成「factory完全不影響前台」。本機驗證：R02019/R02012（都是company_code='F'）改前各看到3份（含1份建大的），改後正確只剩2份（都是建豐的）。已同步部署到遠端（`content.py`/`kenda_contract.py` 備份為 `.bak_20260716c`，restart odoo-server）。

**教訓**：同一份文件裡「這個欄位不影響前台顯示」跟「這個欄位不影響前台可見性/過濾」是兩件不同的事，寫help text或做決策記錄時要講清楚是指UI呈現還是資料過濾邏輯，避免未來自己或別人誤讀成「完全不用管這個欄位」。

## 2026-07-16（第三則）— Jenny 實際點下載按鈕，出現 MISSING_CUSTOMER_CODE 錯誤（已修復）

**狀態**：已解決，本機+遠端都已修復並驗證

**根因**：前台「下載」按鈕是瀏覽器直接導頁到 `download_url`（純連結點擊，不是 JS fetch），這種導頁方式**沒辦法附加自訂 HTTP header**（`X-Customer-Code`／`Authorization: Bearer`），但 `authenticate()` 原本強制要求這兩個 header 才能通過驗證，所以每次點下載都會直接被擋。這不是前端bundle的bug，是後端API設計沒考慮到「檔案下載必須靠純連結導頁、無法夾帶自訂header」這個限制。

**修復**（純後端修改，前端 bundle 完全不用動，因為 `download_url` 是後端動態組出來回傳給前端的資料，不是寫死在bundle裡）：
1. `main.py` 的 `authenticate()` 新增 `allow_query=True` 選項，開啟時 header 缺值可退而改讀 URL query string（`?customer_code=...&token=...`）；預設仍是 `False`，其餘所有 API（購物車、訂單、店招等）維持原本只認 header，不擴大攻擊面。
2. `content.py` 的 `GET /contracts` 回傳的 `download_url` 改成把當次請求驗證通過的 `customer_code`+`token` 直接組進網址查詢字串；`GET /contracts/<id>/download` 改呼叫 `authenticate(allow_query=True)`。
3. 本機驗證：模擬瀏覽器「完全不帶任何自訂header」直接 GET 這個新網址，成功拿到正確 PDF（200、147284 bytes、`%PDF`開頭）。

**安全性備註**：token 會出現在網址列/瀏覽器歷史紀錄/伺服器 access log，但這個平台的 token 本來就是MVP等級的固定值（存在 `ir.config_parameter`，不會過期輪替），不是JWT或有時效性的憑證，跟其餘API維持header-only、只開放這一條下載路徑用query string，風險已控制在最小範圍。
