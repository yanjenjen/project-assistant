## 二、風險條列

### 技術／資料風險

- F005-2 進度查詢一旦切換到新版分頁 API（後端固定每頁 10 筆），若前端沒同步補上分頁 UI，經銷商申請紀錄超過 10 筆會被截斷看不到——目前測試帳號只有 8 筆，本機測不出這個問題，正式上線後資料量變多才會炸。
- F005-2／F005-3 目前都是「一次撈該經銷商全部申請紀錄」，沒有分頁或筆數上限，長期資料量成長會拖慢頁面載入。
- 前端是編譯後的 minified bundle，沒有可讀原始碼（`web-src`／`extracted/src` 都只是編譯輸出的備份，不是真正 source），每次改動都是直接手術壓縮檔＋手動換版號，出錯風險與除錯成本都比一般開發高。過去已發生因忘記換版號、瀏覽器吃到舊快取（immutable cache）導致「改了但沒生效」的狀況。
- 過去發生過遠端與本機 schema 版本落後一整個世代（分類欄位型別不同步），推送前如果沒有先唯讀核對兩端現況，容易誤判「應該已經同步」。
- 曾發生部署 addon 只挑改過的檔案、漏推 `security/ir.model.access.csv`，導致後台使用者權限被擋（ACL Access Denied）。
- 曾發生用字串比對批次清理遠端舊資料（非 UTF-8 髒資料），誤刪合法分類記錄，事後才手動補回——批次清資料前沒有逐筆核實的流程風險。
- 下單流程完全排除庫存即時查詢 API（專案範圍已確認排除），超賣風險由 ERP 端下單後覆核，**平台端本身無防呆**。
- 客戶主檔／產品主檔都是 Excel 一次性匯入＋手動更新，非即時同步——ERP 異動後若忘記重新匯入，前台會顯示過期資料。

### 流程斷點（訂單流程有兩個明確缺口）

- 經銷商下單後，**沒有任何 mail 通知**（業務確認通知、訂單狀態變更通知經銷商）——目前完全靠人工登入後台查看，容易漏單。
- 後台目前只能「查看」訂單狀態，**沒有手動確認/成立訂單的操作介面**，若業務確認是必要關卡，現在的系統做不到。
- 這兩點在 7/7 稽核 PPT 上都明確標「仍待確認」：業務確認是否為必要步驟？mail 該在哪個節點觸發？**這是需要建大方拍板的開放問題，不是艾創點自己能決定的技術細節。**

### 權限／資安風險（已知、刻意延後處理）

- 依 Jenny 7/16 裁示，「經銷商可看哪些申請類別／施工項目」「各廠商企只能維護自己廠資料」這類細部權限卡控，目前全部未做，所有內部 Odoo 使用者共用最寬鬆權限（`base.group_user`），統一延後到最後一次處理。正式上線前若沒排進時程，會是資安與誤改資料的破口。

### 外部依賴風險

- F005-2「申請進度」（`apply_progress`）欄位要等建大 BPM 系統做好才能串接，目前留空——這不在艾創點掌控範圍內，進度完全取決於建大那邊的時程。
- 業績／獎金／對帳查詢三個模組的計算邏輯全部在 ERP 端完成，平台只接收「最終數字」，這是雙方已確認的架構原則，但代表**這三個查詢功能的正確性完全依賴 ERP 端 API 是否已如期完成介接**，目前 PPT 上仍是規劃中的 API 清單，需跟建大 ERP 團隊確認實際介接進度。

### 流程／文件風險（本輪盤點的核心發現）

- **240 功能需求管理系統本身沒有涵蓋專案全部範圍**：帳號管理、業績／獎金／對帳查詢等已完成的核心模組完全沒有 F0xx 編號，只存在一份 PPT 稽核簡報裡。這些功能沒有進追蹤系統，代表沒有正式驗收記錄、沒有問題追蹤，未來有 bug 或客戶提出異動需求時容易不知道該歸檔到哪裡。
- F001 有一批 2026-07-06 提出、已確認要改的 UI 需求（MC／PCR／BC 三份文件，內容包含 ETRTO／TPI／PSI 規格欄位、模糊搜尋邏輯、報價單預設、訂購數字輸入方式等），**目前不確定是否已實作**，且完全沒被 240 系統登記追蹤。
- F006 的完成度判斷在兩份紀錄（7/7 稽核 PPT vs 7/16 驗收記憶）之間有落差，沒有一份文件把兩者對齊。
- F002 有明確待辦（31 筆訂單匯入）但尚未排入執行。
- INDEX.md 總覽表更新頻率跟不上實際進度，若以 INDEX.md 判斷進度，目前會看到過時資訊。
