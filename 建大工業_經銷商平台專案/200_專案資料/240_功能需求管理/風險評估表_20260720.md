## 一、白話總結（給趕時間看的人）

- 系統本身做得比原本的追蹤文件顯示的還多，很多功能程式碼看起來已經存在，但**沒有一項是走過完整測試／客戶驗收流程的**——目前的「✅已完成」都只是 AI 讀程式碼的初步判斷，不是實測結果。
- 下單流程有兩個明顯缺口：**客戶下單後系統不會寄信通知任何人**、**後台沒有「確認訂單」這個操作按鈕**，發信功能需要建大提供 O365 串接資料、客戶信箱，並依據排程作業。
- 有 5 個已經做完的功能（帳號管理、訂單查詢、業績查詢、獎金查詢、對帳查詢），**先前完全沒有編號、沒有進追蹤系統**，本輪已經補登記（F007–F011），但都還沒測試。
- 有一批 7/6 客戶提出的下單畫面調整需求（規格欄位、搜尋方式等），**目前只確認了「要改什麼」，還沒寫成正式的開發指令、也還沒開始動工**。
- 「全站 Banner／語系切換」卡在客戶還沒決定要用哪一張 Banner 圖，不是艾創點這邊沒做完。
- 「店招申請－申請書」還缺的兩件事（通知業務、依地區自動帶施工項目），**要等建大的 BPM 系統做好，才會知道實際該怎麼做**，不是艾創點技術上做不到。
- 「合約下載」原本有兩份紀錄講法不一致，**已核對確認：以 2026-07-16 的驗收紀錄為準，功能已完成**，較舊的 7/7 稽核簡報是過時資訊。

## 二、專案時程風險檢視

**依目前時程**：8/15 所有 API 串接完成 → 8/16-8/31 留給客戶微調 → 9 月建大＋經銷商系統測試 → 10 月教育訓練 → 11 月正式上線。距離 8/15 大約 3.5 週，目前看到三類卡點：

### 卡點一：建大 ERP 端 6 支 API＋BPM——以建大給的「最慢繳交日」（D欄）為準

排程追蹤表（`建大工業_專案時程追蹤表_v0.5.xlsx`）裡，C欄「預期月與週別」只是初步預排的工作週次，**真正算數的是 D 欄「預期完成」——這是建大明確答應 Jenny 的最慢繳交日**：

| 項目 | 最慢繳交日（D欄） |
|---|---|
| 獎金查詢 API | **2026-07-24（4 天後）** |
| 對帳查詢 API | **2026-07-24（4 天後）** |
| 報價同步 API | 2026-07-31 |
| Mail 寄信通知 | 2026-07-31 |
| BPM 表單流程介接 | 2026-08-07 |
| 下訂單同步 API | 2026-08-07 |
| 訂單查詢 API | **沒有填交付日** |
| 業績查詢 API | **沒有填交付日** |

**這張表用 D 欄看，其實都在 8/15 之前，跟目標是對得上的**，比原本用 C 欄推算的「拖到 8/21」更樂觀。但有兩個地方需要跟建大確認：

1. **「訂單查詢 API」「業績查詢 API」這兩項完全沒有填交付日**，是目前唯一沒有承諾日期的兩支，需要主動跟建大補要日期。
2. **交付日的順序跟工作排程對不太起來**——例如「獎金查詢」「對帳查詢」的工作週次排在 8 月初，交付日卻是最早的 7/24；「報價同步」工作週次排在 7 月上旬，交付日卻是 7/31。不確定是排程表本身還沒更新一致，還是 D 欄另有含意，建議跟建大核對一次，確保雙方看的是同一份「最終交付日」認知。
3. 「BPM 表單流程介接」「Mail 寄信通知」這兩項在表上仍註記「是否在合約範圍內尚未確認」，即使有交付日（8/7、7/31），範圍本身沒定案的話，日期也可能隨之變動，建議跟前面的日期確認一起處理。

### 卡點二：艾創點這邊還沒做完、需要排進 8/15 前處理的部分

- 帳號管理／訂單查詢／業績查詢／獎金查詢／對帳查詢：目前**只有框架**，還沒依需求逐項核對細節，8/15 前要先確認建大有沒有反映過調整意見、再跑一輪本機測試，不能只因為框架存在就算「串接完成」。
- 店招申請－進度查詢：後端已驗證，但前台還沒換成新版查詢（現在用的舊寫法有資料被截斷的風險），需要排進 8/15 前處理。
- 下單流程：購物車完整功能（多圖/影片、加減刪除）、後台訂單確認按鈕，目前都還沒做完。
- 下單流程要不要「業務確認」這道關卡、通知信該在哪個時間點寄，這兩個問題還沒釐清，需要先排時間確認，才能排進開發時程，另等待 API 提供串接。

### 卡點三：完全卡在建大方決策，時程不確定——這幾項若 8/15 前沒定案，會變成 9 月測試才爆出來的破洞

- 店招申請「處理進度」要串 BPM，**沒有確認的 BPM 交付時間**，建議現在就跟建大要一個明確日期，否則這塊到 9 月系統測試時依然是空的。

### 8/16-8/31 客戶微調期可以排的

- 全站 Banner／語系切換：等客戶決定要用哪張圖，這段時間剛好可以拿去問、去調。
- 7/6 提出的下單畫面調整需求：**前提是要在 8/15 前先把需求寫成正式開發指令**，不然拖到 8/16 才開始寫需求，會直接吃掉原本規劃給微調的時間。

### 9 月系統測試前必須確認完成

- 合約下載的後台上載／刪除／修改操作，目前只測過前台下載，後台操作要在開放測試前補測。
- 卡點三提到的建大決策項目，如果拖太晚才拍板，開發＋測試時間會被壓縮到 9 月測試期間才做，等於邊測邊開發，風險較高。

### 本輪新發現：只有框架、完全沒編號、沒人追蹤的功能

以下功能目前**只有基礎框架**（資料表、API 路由都存在），但 Jenny 還沒依照實際需求逐項核對功能細節與設定是否正確——這本來就還沒輪到，依排程表這批工作的開發窗口是 7/28–8/1，現在還沒到。也**先前完全沒有登記在追蹤系統裡**，本輪已經補登記編號（F007–F011）：

- 帳號管理——經銷商可以自己開多個子帳號分開登入，也可以自己改個人資料（但改了不會同步回建大的客戶系統，兩邊資料可能會慢慢兜不起來）
- 訂單查詢——經銷商可以在網站上看自己的訂單狀態（含出貨、發票進度），資料即時跟建大系統要
- 業績查詢——經銷商可以查自己（或底下經銷商）的業績，數字由建大系統算好直接給
- 獎金查詢——邏輯跟業績查詢一樣，但建大系統只給最終獎金數字，不給明細，經銷商如果對金額有疑問目前只能靠業務口頭說明
- 對帳查詢——邏輯跟業績查詢一樣，查對帳金額、發票、折讓

**待確認**：建大是否已經針對這幾個功能的細節（例如要顯示的欄位、篩選邏輯）反映過需要調整的地方？如果有，需要先找出來核對，不能只憑目前的框架判斷有沒有做對。

### 本輪新發現：下單流程實際完成度

- 商品瀏覽（分類、搜尋、排序、規格篩選）已經做完
- 商品詳情頁已經做完；但**多張圖片／影片展示、購物車的完整加減／刪除功能**還沒做完
- 前台結帳、把訂單送去建大系統，已經做完
- 後台可以看訂單列表和狀態，但**業務要「確認」訂單這個操作按鈕還沒做**——已直接查過程式碼確認，目前系統真的沒有這個功能，不是文件沒寫而已
- **訂單狀態變更後，完全不會寄信通知任何人**（不管是通知業務還是通知經銷商）——已直接查過程式碼確認，這件事完全沒開始做

## 四、風險條列

### 系統本身的技術風險

| 風險 | 影響 |
|---|---|
| 進度查詢換新版查詢卻沒做換頁 | 申請超過 10 筆會被截斷看不到，測試帳號只有 8 筆測不出來 |
| 進度查詢／到期列表一次抓全部資料 | 資料變多會拖慢網頁 |
| 前端程式是壓縮打包的，改動要動手術 | 過去發生過改了忘記換版號，使用者還是看到舊畫面 |
| 本機／客戶測試網站版本曾差一整個世代 | 推送前沒先核對，容易誤判已經同步 |
| 曾漏推一個權限設定檔 | 後台使用者被擋在功能外面 |
| 曾用比對文字批次清資料 | 誤刪過一筆合法資料 |
| 下單流程沒有即時庫存查詢（雙方已確認排除） | 賣超要靠建大事後把關，平台不會攔 |
| 客戶／商品資料是 Excel 匯入非即時同步 | 忘記重新匯入會顯示舊資料 |

### 訂單流程的兩個明確缺口

| 風險 | 影響 |
|---|---|
| 下單後系統不會寄任何通知信 | 只能靠人工登入後台查看，容易漏單 |
| 後台沒有「確認/成立訂單」按鈕 | 若業務確認是必要關卡，現在系統做不到 |

**這兩點目前還沒確認，不是建大卡在決策，是 Jenny 這邊還沒空一個一個盤查釐清。**

### 權限管理風險（已知、雙方講好先不處理）

**所有後台使用者現在共用最寬鬆權限**，不分職務、不分廠別（例：誰能看哪些申請類別、誰只能維護自己廠資料，都還沒卡控）。雙方講好等最後統一處理，但**正式上線前沒排進時程，會是資安破口**。

### 依賴建大那邊的風險（不在艾創點掌控範圍）

| 風險 | 影響 |
|---|---|
| 「處理進度」要等建大 BPM 做好才能串 | 進度完全看建大那邊 |
| 申請書「自動通知業務」「依地區帶施工項目」也卡 BPM | 不是艾創點技術做不到，是還不知道怎麼設計 |
| 業績／獎金／對帳數字全部由建大系統算好給 | 這三個功能對不對，完全取決建大端介接有沒有如期完成 |

### 追蹤與文件本身的風險（本輪盤點的核心發現）

- **追蹤系統沒有涵蓋全部範圍**：帳號管理、業績／獎金／對帳查詢已經做完，但先前完全沒編號、沒有驗收紀錄，只存在一份簡報裡。
- 7/6 下單畫面調整需求，只確認了內容，沒寫成開發指令、沒登記追蹤。
- 「訂單匯入」有明確待辦（31 筆）但還沒排時程。
- **內部總覽表更新速度跟不上實際進度**（合約下載是一例，已核對更新），光看總覽表容易誤判進度。

## 六、暫緩事項（與本輪風險盤點無關，之後有空再做）

**搜尋功能是刻意統一延後處理，不是漏掉**：平台裡有好幾個地方（例如「進度查詢」頁面）都需要一個「搜尋」功能窗，而且都需要做成模糊搜尋（不是完全比對）。因為很多地方都有同樣的需求，Jenny 的決定是**不要一個一個分開做，等一次把所有地方要用到的搜尋窗盤點清楚，統一設計、一起調整**，避免同一個功能改好幾次、邏輯不一致。

以「進度查詢」頁面為例，之後要做的話大致方向是：加一個搜尋欄（可以用車行名稱、廣告物編號、經銷商、地址查）、加上一頁／下一頁的換頁功能、資料來源改接已經寫好且驗證過的新版查詢功能。「到期列表」頁面不受影響，維持現狀。

**待辦**：需要先盤點清楚「所有區塊」具體是指哪幾個頁面／功能都需要這個搜尋窗，才能一次設計、一次調整，目前這份清單還沒整理出來。
