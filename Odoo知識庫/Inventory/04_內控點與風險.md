## 一、收貨流程內控點

### IC-RCV-01：到貨數量核對
| 項目 | 說明 |
|-----|-----|
| 風險 | 實際到貨數量與採購訂單不符，庫存記錄錯誤 |
| 控制措施 | 收貨單 Demand（訂購量）vs Quantity（實際量）逐行核對；差異須手動調整並說明原因 |
| Odoo 機制 | 系統顯示 Demand 欄供比對；數量不符時可選擇 Create Back Order（等候剩餘）或 No Back Order |
| 責任人 | 倉庫操作員（接收）、倉庫經理（審核差異） |

### IC-RCV-02：儲位設定正確性
| 項目 | 說明 |
|-----|-----|
| 風險 | 收貨設定錯誤的 Destination Location，導致庫存實際位置與系統不符 |
| 控制措施 | 收貨驗收前確認表頭 Destination Location；驗收後於 Physical Inventory 確認儲位 |
| Odoo 機制 | Putaway Rules 可自動路由至正確儲位；若發現錯誤可使用 Actions → Relocate 修正 |
| 責任人 | 倉庫操作員 |

### IC-RCV-03：Back Order 追蹤
| 項目 | 說明 |
|-----|-----|
| 風險 | 部分到貨後未追蹤 Back Order，造成漏收或重複採購 |
| 控制措施 | 選擇 Create Back Order 而非 No Back Order；定期檢視收貨儀表板中的待收清單 |
| Odoo 機制 | Back Order 自動建立並與原 PO 連結，Smart Button 可追蹤 |
| 責任人 | 採購/倉庫經理 |

### IC-RCV-04：落地成本入帳
| 項目 | 說明 |
|-----|-----|
| 風險 | 進口稅、運費等附加成本未分攤至商品成本，高估利潤 |
| 控制措施 | 確認以 Service 類型產品代表落地成本；在廠商帳單確認前建立 Landed Cost 並關聯收貨單 |
| Odoo 機制 | Landed Cost 功能（需啟用）分攤至各品項，更新庫存估值 |
| 責任人 | 採購、財務 |

## 二、出貨流程內控點

### IC-DLV-01：出貨前庫存確認
| 項目 | 說明 |
|-----|-----|
| 風險 | 庫存不足卻仍驗收出貨，導致帳物不符 |
| 控制措施 | 確認 Product Availability 欄位顯示綠色 Available 再 Validate；2 步驟流程需先完成 Pick 才能 Deliver |
| Odoo 機制 | 系統防止未保留庫存的出貨；Reservation Method 控制何時保留 |
| 責任人 | 倉庫操作員 |

### IC-DLV-02：出貨政策一致性
| 項目 | 說明 |
|-----|-----|
| 風險 | 不同訂單採用不同出貨策略，造成客戶體驗不一致或財務困擾 |
| 控制措施 | 確認 Picking Policy 設定（Ship All at Once vs Ship as Available）符合業務需求 |
| Odoo 機制 | 統一在 Inventory → Settings → Picking Policy 設定全公司策略 |
| 責任人 | 倉庫/業務經理 |

### IC-DLV-03：退貨作業識別
| 項目 | 說明 |
|-----|-----|
| 風險 | 退貨與一般收貨混在一起，無法快速識別退貨數量與原因 |
| 控制措施 | 建立自訂 Returns Operation Type（序號前綴 RE）；在儀表板顯示獨立的退貨卡片 |
| Odoo 機制 | Delivery Orders → Returns Type 指定退貨作業類型；可搭配 QCP 進行品質檢查 |
| 責任人 | 倉庫經理 |

### IC-DLV-04：退貨品質管控
| 項目 | 說明 |
|-----|-----|
| 風險 | 損壞退貨品重新入庫後出售給其他客戶 |
| 控制措施 | 搭配 Quality Control Point（QCP）在退貨時強制品質檢查；失敗品設定 Failure Location（不進主倉） |
| Odoo 機制 | QCP 設定於退貨 Operation Type；失敗後自動轉至指定隔離儲位 |
| 責任人 | 品質管控人員 |

## 三、庫存盤點與調整內控點

### IC-INV-01：盤點差異處理
| 項目 | 說明 |
|-----|-----|
| 風險 | 盤點差異未調查原因，長期累積損失無法追蹤 |
| 控制措施 | Apply 庫存調整時必須填寫原因（Reason 欄位）；差異超過閾值時須主管審核 |
| Odoo 機制 | 調整記錄寫入 Moves History 可供稽核；Physical Inventory 顯示 Difference 欄 |
| 責任人 | 倉庫經理 |

### IC-INV-02：循環盤點執行
| 項目 | 說明 |
|-----|-----|
| 風險 | 年度大盤才發現缺損，損失金額龐大且難以追查原因 |
| 控制措施 | 針對高周轉或高價值儲位設定每月（30天）循環盤點頻率 |
| Odoo 機制 | Cyclic Counting Frequency 自動安排下次盤點日期；可透過 Request a Count 分派任務 |
| 責任人 | 倉庫經理、指定盤點員 |

### IC-INV-03：易腐品過期管控
| 項目 | 說明 |
|-----|-----|
| 風險 | 過期商品流向客戶，造成法規問題與品牌損失 |
| 控制措施 | 啟用 Expiration Dates；設定 FEFO 移除策略優先出售即將到期品；定期篩選 Expiration Alert 過濾器 |
| Odoo 機制 | Lots/Serial Numbers 頁面 → Filter: Expiration Alert 顯示即將到期品；到達 Alert Date 自動通知 Responsible 使用者 |
| 責任人 | 倉庫操作員、品質管控 |

### IC-INV-04：報廢品財務影響
| 項目 | 說明 |
|-----|-----|
| 風險 | 報廢品未正確記帳，損益表缺少相關損失 |
| 控制措施 | 設定 Scrap Location（Inventory Loss 類型）並指定 Loss Account；報廢時選擇正確的 Scrap Location |
| Odoo 機制 | Operations → Scrap 建立報廢單；Scrap 金額自動出現於 Accounting → Reports → Profit & Loss |
| 責任人 | 倉庫操作員、財務 |

## 四、補貨與規劃內控點

### IC-REP-01：補貨規則設定合理性
| 項目 | 說明 |
|-----|-----|
| 風險 | Min/Max 設定不當，造成缺貨或過量庫存 |
| 控制措施 | 定期檢視 Replenishment Dashboard；確認補貨規則的最小量與業務需求相符 |
| Odoo 機制 | Forecasted Quantity 包含未出貨的 SO，避免重複補貨；Suggested Quantity = Max - Forecasted |
| 責任人 | 倉庫/採購經理 |

### IC-REP-02：MTO 產品濫用
| 項目 | 說明 |
|-----|-----|
| 風險 | 高頻訂購的一般品設為 MTO，造成每次下單都觸發採購，增加行政負擔 |
| 控制措施 | MTO 僅適用低頻、高客製化或高成本商品；一般庫存品使用 Reordering Rules |
| Odoo 機制 | 產品 Inventory Tab → Routes 設定；MTO 需搭配 Buy 或 Manufacture 路線 |
| 責任人 | 庫存/採購規劃師 |

### IC-REP-03：多倉庫補貨地址設定
| 項目 | 說明 |
|-----|-----|
| 風險 | 倉庫地址設定錯誤（如補貨倉與收貨倉地址相同），導致配送文件錯誤 |
| 控制措施 | 每個倉庫需有唯一地址；子倉庫（店面）地址應為店面實際地址 |
| Odoo 機制 | Warehouse 主檔的 Address 欄位決定收貨地址，顯示於所有相關文件 |
| 責任人 | 系統管理員、倉庫經理 |

## 五、追蹤性相關控制

### IC-TRC-01：批號/序號接收強制性
| 項目 | 說明 |
|-----|-----|
| 風險 | 接收時未記錄批號，事後無法追蹤商品來源（召回困難） |
| 控制措施 | Odoo 強制：Validate 前若未填批號/序號，系統彈出錯誤阻止驗收 |
| Odoo 機制 | 系統驗證 Lot/Serial Number 必填（依產品 Tracking 設定） |
| 責任人 | 倉庫操作員 |

### IC-TRC-02：序號唯一性
| 項目 | 說明 |
|-----|-----|
| 風險 | 重複使用序號，無法區分個別產品歷史 |
| 控制措施 | 使用 Generate Serials/Lots 系統自動產生流水序號，避免人工錯誤 |
| Odoo 機制 | Generate 功能確保序號在產品範圍內不重複 |
| 責任人 | 倉庫操作員 |

### IC-TRC-03：寄售庫存隔離
| 項目 | 說明 |
|-----|-----|
| 風險 | 寄售品被誤計入公司庫存價值，高估資產 |
| 控制措施 | 接收寄售品時必須設定 Assigned Owner；定期確認 Inventory Valuation 報表中寄售品估值為 $0 |
| Odoo 機制 | 系統依 Owner 欄位自動排除寄售品庫存估值 |
| 責任人 | 倉庫經理、財務 |

### IC-TRC-04：移除策略一致性
| 項目 | 說明 |
|-----|-----|
| 風險 | 不同儲位或類別設定衝突的移除策略，揀貨時出現不可預期的選擇 |
| 控制措施 | Product Category 的移除策略優先於 Location；確認策略層級設定不衝突 |
| Odoo 機制 | Force Removal Strategy（Product Category 層級）覆蓋 Location 層級設定 |
| 責任人 | 倉庫/系統管理員 |

## 六、權限設計建議（Access Rights for Inventory Teams）

### 標準角色矩陣

| 功能模組 | 倉庫操作員 | 倉庫經理 | 採購經理 | 財務 |
|---------|-----------|---------|---------|-----|
| Inventory（App） | User | Administrator | - | - |
| Purchase（App） | - | Administrator | Administrator | - |
| Manufacturing（App） | - | Administrator | - | - |
| Barcode（App） | 自動取得 | 自動取得 | - | - |
| Quality（App） | - | User | - | - |
| Accounting（App） | - | - | - | User/Admin |
| Documents（App） | - | User（自身） | - | - |
| Settings（Admin） | 否 | 否 | 否 | 否 |

### 關鍵原則（來自 INV08）
1. **最小權限原則**：操作員僅取得 Inventory User 權限，不應有 Administrator 等級
2. **防止誤改設定**：操作員無 Purchase / Manufacturing 存取，避免誤改 BOM 數量或工作站
3. **透過 Barcode App 執行**：操作員的日常任務（收貨、移轉）透過 Barcode App 完成，不直接修改系統設定
4. **角色分離**：採購（Product Manager → 下 PO）與倉庫（驗收 Receipt）由不同人員執行

### 常見誤配風險

| 誤配情境 | 風險 |
|---------|-----|
| 操作員獲得 Manufacturing Admin | 可修改 BOM、關閉工作站，影響生產計畫 |
| 操作員獲得 Purchase Admin | 可自行確認 PO、繞過採購審核 |
| 所有人共用管理員帳號 | 操作無法追蹤，稽核困難 |
| 未分配 Inventory 權限但指定盤點 | 操作員無法在 Barcode App 完成盤點任務 |

## 七、倉庫設計內控建議

### 多步驟流程 vs 內控效果

| 流程複雜度 | 優點 | 適用情境 |
|-----------|-----|---------|
| 1 步驟收貨 | 快速、低行政負擔 | 小型倉庫、全部到即全部上架 |
| 2 步驟收貨 | 輸入區與庫存區分離，排序後再上架 | 需分揀的大批入貨 |
| 3 步驟收貨 | 增加品質管控關卡（Input → QC → Stock） | 高價值或需驗品的商品 |
| 1 步驟出貨 | 快速出貨，適合小量訂單 | 小型倉庫、直接出貨 |
| 2 步驟出貨 | 揀貨團隊與出貨團隊分工，責任明確 | 中大型倉庫、有揀貨專員 |
| 3 步驟出貨 | 揀→包→出，每步驟獨立驗證 | 高複雜度、多組件包裝、嚴格品管 |

> **KISS 原則（INV03）**：不必要的步驟增加會帶來更多待處理作業，應以業務實際需求為準，避免過度複雜。
