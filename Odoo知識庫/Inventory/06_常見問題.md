## 一、基礎概念類

### Q1：Lot（批號）和 Serial Number（序號）有什麼差別？什麼情況下用哪一個？

**A：**
| 比較項目 | Lot（批號） | Serial Number（序號） |
|---------|-----------|-------------------|
| 追蹤單位 | 一組同批次商品（多件共用一個號碼） | 每一件獨立一個號碼 |
| 適用商品 | 食品、藥品、原物料（同批次管理） | 電子設備、機械、高價品（個別管理） |
| 數量限制 | 一個批號可對應多個數量 | 一個序號只能對應 1 件 |
| 常見場景 | 生產批次、到期日追蹤 | 保固追蹤、特定設備維修記錄 |

選擇建議：若需要「個別設備維修記錄」或「單件保固」→ Serial Number；若只需「同批次召回」或「到期日管理」→ Lot。（參考 INV13、INV14）

---

### Q2：Packaging 和 Package 有什麼差別？常常搞混，怎麼區分？

**A：**
- **Packaging（包裝規格）**：代表銷售或採購時的「標準化數量單位」，定義在產品主檔，如 Bolt（100碼布一匹）、Six-Pack（6罐一組）。是一種「規格定義」，不是實體容器。
- **Package（包裹）**：倉庫移動時的「實體容器」，如 PACK00000019 這個紙箱，裡面可放不同產品不同數量。是一個實際存在的物件，系統會賦予唯一編號。

**記憶方式**：Packaging = 「規格」（在訂單上），Package = 「箱子」（在倉庫裡）。（參考 INV22、INV23）

---

### Q3：Routes（路線）、Rules（規則）和 Operation Types（作業類型）是什麼關係？

**A：**
- **Operation Type**（作業類型）：定義一種移轉的類型（如 Receipt、Delivery、Pick、Internal），決定前置與目標儲位、序號前綴等。
- **Rule**（規則）：Push Rule 或 Pull Rule。描述「當什麼條件成立時，觸發什麼作業類型的移動」。
- **Route**（路線）：一組 Rules 的集合，代表一條完整的補貨或流通路徑（如「Buy」路線 = 觸發採購的 Pull Rule；「Multi-step delivery」路線 = 包含 Pick → Pack → Deliver 的多條 Rules）。

**關係**：Route 包含多條 Rule，每條 Rule 對應一個 Operation Type。（參考 INV06、INV07）

---

### Q4：FIFO、LIFO、FEFO 移除策略的差別是什麼？哪種最常用？

**A：**
| 策略 | 全名 | 移除順序 | 最常用情境 |
|-----|-----|---------|---------|
| FIFO | First In First Out | 最早入庫的先出 | 一般商品、防止庫存老化 |
| LIFO | Last In First Out | 最後入庫的先出 | 某些特殊原物料情境 |
| FEFO | First Expiry First Out | 最早到期的先出 | 食品、藥品、化妝品（易腐品） |
| Closest Location | 最近儲位優先 | 距離出口最近的儲位先揀 | 大型倉庫優化揀貨路徑 |
| Least Packages | 拆包最少優先 | 避免拆開整箱 | 希望維持整箱完整性 |

實務上 **FIFO** 最常見（避免庫存老化）；有到期日需求的則用 **FEFO**。LIFO 在財務會計方面有其意義，但庫存操作上較少用。（參考 INV16）

---

### Q5：庫存保留方式（Reservation Method）有哪三種？如何選擇？

**A：**
- **At Confirmation**：銷售訂單確認時立即鎖定庫存。適合客戶要求快速確認的場景，但可能讓庫存長期被鎖定。
- **Manual**：不自動保留，等倉庫人員手動 Check Availability 或使用 Reserve 功能。適合需要人工判斷優先順序的情境。
- **Before Scheduled Date**：出貨前 N 天自動保留（N 天在 Security Lead Time 設定）。兼顧系統自動化與避免過早鎖定。

設定位置：Inventory → Configuration → Operation Types → Delivery → Reservation Method。（參考 INV05）

## 二、操作流程類

### Q6：收貨時到貨數量和訂購量不符，應該怎麼處理？

**A：** 兩個選項：
1. **Create Back Order**：本次只驗收到的部分（修改 Quantity 欄），剩餘量系統自動建立新的待收單（Back Order），等廠商補貨。
2. **No Back Order**：視為本次訂單結束，不再追蹤剩餘量。

操作：在 Operations Tab 將 Quantity 欄改為實際到貨數 → Validate → 選擇 Create Back Order 或 No Back Order。

控制點：Back Order 應在 Receipt Smart Button 中追蹤，避免漏收。（參考 INV02）

---

### Q7：出貨單的 Product Availability 顯示的顏色/日期代表什麼意思？

**A：**
- **綠色（Available）**：庫存充足，已保留，可直接 Validate。
- **黃色**：庫存存在但尚未正式保留（需手動 Check Availability）。
- **顯示日期（如 07/30）**：部分庫存尚未到位，預計該日期才可用（通常是預計到貨日）。
- **紅色 / 空白**：庫存不足，無法出貨。

若顯示日期，表示需等待補貨才能完整出貨。（參考 INV02）

---

### Q8：Putaway Rules（上架規則）和 Storage Category（儲存類別）是什麼？有什麼用？

**A：**
- **Putaway Rules**：當商品進入倉庫時，系統自動將商品路由到指定的子儲位。規則設定「哪種產品/類別→應放到哪個儲位」。
- **Storage Category**：定義儲位的「容量與特性」（最大重量、高度、承載量），並可設定「Closest Location」或「Last Used Sublocation」邏輯決定選哪個空位。

**搭配使用**：Storage Category 先篩選符合尺寸要求的儲位，Putaway Rule 再決定最終放哪格。（參考 INV19）

---

### Q9：什麼是 Cross-Docking（越庫作業）？什麼情況下適合使用？

**A：** Cross-Docking 是指從採購入庫的商品「不入主倉庫」，直接在收發轉運區等待，隨即轉移到客戶出貨作業。貨物從 Dock In（收貨碼頭）→ Crossdock → Dock Out（出貨碼頭），幾乎不在倉庫停留。

適合情境：
- 貨品是特定客戶訂單的直送商品
- 倉儲空間有限，不希望暫存
- 高周轉、低保存需求的商品

設定方式：在倉庫啟用 Cross-Docking Route，在產品或銷售訂單指定此路線。（參考 INV07）

---

### Q10：Batch Transfer、Wave Transfer、Cluster Transfer 三者有什麼差別？

**A：**
| 類型 | 主要邏輯 | 適用場景 |
|-----|---------|---------|
| Batch Transfer（批次移轉） | 將多張揀貨單合併給一位揀貨員，一趟完成 | 中小型倉庫，一人多單揀貨 |
| Wave Transfer（波次移轉） | 依倉庫區域（Location）分組，不同揀貨員負責不同區 | 大型倉庫，分區作業 |
| Cluster Transfer（集群移轉） | 一名揀貨員同時服務多張訂單，邊揀邊依訂單分類放入包裹 | 電商倉庫，高密度訂單，揀完即分件 |

三者均需啟用 Batch/Wave/Cluster 設定，且通常配合 2 步驟以上的出貨流程（需有 Pick 步驟）。（參考 INV28、INV29、INV30）

---

### Q11：寄售庫存（Consignment）的庫存估值為什麼是 $0？

**A：** 因為 Assigned Owner 設定為廠商（如 Wood Hut），代表這批商品的所有權仍屬於廠商，只是物理上放在本公司倉庫。Odoo 庫存估值（Inventory Valuation）只計算「公司擁有」的庫存，寄售品屬於廠商資產，因此估值 = $0。

在手數量（On Hand Quantity）仍會顯示（物理存在），但不計入財務報表中的庫存資產。（參考 INV32）

## 三、設定與進階類

### Q12：Multi-Step Routes（多步驟路線）和倉庫設定中的 1/2/3 Steps 是什麼關係？

**A：**
- 倉庫設定中選擇 Incoming/Outgoing Shipments 的步驟數（1/2/3），是快捷設定，背後自動建立對應的 Routes 和 Rules。
- **1 步驟收貨**：Vendor → Stock（直接到主倉）
- **2 步驟收貨**：Vendor → Input → Stock（先放 Input 區，再上架）
- **3 步驟收貨**：Vendor → Input → Quality Control → Stock（多一道品管）
- 出貨同理：3 步驟 = Pick（揀貨）→ Pack（打包）→ Deliver（出貨）

選擇步驟數後，Inventory → Configuration → Routes 中會自動出現對應路線與規則。（參考 INV03、INV06）

---

### Q13：補貨規則中的 Forecasted Quantity（預測數量）是怎麼計算的？為什麼不是只看在手數量？

**A：**
預測數量計算公式：
**Forecasted Qty = On Hand + 確認中的 PO 收貨量 - 已確認的 SO 出貨量**

原因：若只看 On Hand 決定是否補貨，可能在已有「即將到貨的 PO」或「等待出貨的 SO」的情況下，誤觸發重複補貨。預測數量把已知的進出流量都納入，讓補貨決策更準確。（參考 INV17）

---

### Q14：落地成本（Landed Costs）有哪幾種分攤方式？應該如何選擇？

**A：**
| Split Method | 計算邏輯 | 適用情境 |
|-------------|---------|---------|
| Equal（等額分攤） | 總金額 ÷ 收貨品項數量 | 各品項同等重要，費用難以區分 |
| By Quantity | 依各品項數量比例分攤 | 按件數計費（如每箱固定處理費） |
| By Current Cost | 依各品項目前成本比例分攤 | 保險費、進口稅（高值品承擔更多） |
| By Weight | 依各品項重量比例分攤 | 運費（重的承擔更多） |
| By Volume | 依各品項體積比例分攤 | 運費（體積大的承擔更多） |

實務建議：運費用 By Weight 或 By Volume；保險費用 By Current Cost；一般附加費用 Equal。（參考 INV35）

### Q15：Barcode App 的操作員帳號需要哪些存取權限設定？

**A：** 根據 INV08 的說明：
1. 操作員帳號需要 **Inventory（庫存）** 存取層級設定為「User」→ 系統自動授予 Barcode App 的操作權限
2. 不需要也不應設定 Inventory Administrator（避免誤改系統設定）
3. 不應開放 Purchase App 存取（避免操作員自行建立 PO）
4. 不應開放 Manufacturing App 存取（避免誤改 BOM 或工作站）

Barcode App 的存取控制與 Inventory App 綁定，有 Inventory User 就可以使用 Barcode App 執行收貨、盤點、揀貨等作業。（參考 INV08）

---

### Q16：MTO（Make to Order）路線和 Reordering Rules（補貨規則）有什麼不同？什麼情況下用哪一個？

**A：**
| 比較項目 | MTO | Reordering Rules |
|---------|-----|-----------------|
| 觸發方式 | 每次 SO 確認時立即觸發 | 庫存低於 Min 時觸發（或手動 Order） |
| 採購時機 | 每筆訂單各觸發一次採購 | 多筆訂單累積後一起補 |
| 適用品項 | 高度客製化、低頻訂購 | 標準品、高頻訂購 |
| 庫存停留 | 幾乎不積庫存（直達客戶） | 有安全庫存，隨時可出貨 |

影片特別提醒：MTO 不適合一般常售商品，否則每次下單都觸發採購，行政負擔大且無法批量採購降低成本。（參考 INV17）

### Q17：何時應該建立新的 Operation Type（作業類型）而不是使用預設的？

**A：** 以下情境建議建立自訂 Operation Type：
1. **退貨管理**：建立專屬 Returns Operation Type（前綴 RE），讓退貨在儀表板獨立顯示，便於識別與追蹤
2. **多倉庫**：新增倉庫時，Odoo 會自動產生該倉庫的 Receipt/Delivery，但若有特殊流程（如品管隔離入庫），需手動建立
3. **品質檢查點**：搭配 Quality App 設定特定 Operation Type 觸發 QC 點
4. **跨公司移轉**：特殊的 Inter-Company Transfer Operation Type

預設的 Receipt、Delivery、Internal Transfer 能滿足大多數標準流程。（參考 INV09）

### Q18：單據系統中的 Scheduled Date、Deadline 和 Lead Time 的關係是什麼？

**A：**
- **Customer Lead Time**（產品設定）：從下單到客戶收到的承諾天數。影響 SO 上的 Delivery Date 計算。
- **Vendor Lead Time（Purchase Tab）**：廠商從接單到出貨的天數。影響 PO 上的 Expected Arrival 計算。
- **Security Lead Time**（全局設定）：額外緩衝天數，在 Scheduled Date 前就保留庫存或觸發採購。
- **Scheduled Date（出貨單）**：系統計算的預計出貨日 = SO 確認日 + Customer Lead Time - Security Lead Time。
- **Deadline（出貨單）**：最晚必須出貨的日期，超過則警示（橘色）。

這些日期共同組成 Odoo 的「排程與前置時間」體系，協助系統在正確時間點提醒採購與倉庫。（參考 INV18）

---

### Q19：DMS（Dispatch Management System，配送管理系統）是什麼？需要什麼條件才能啟用？

**A：** DMS 是 Odoo Inventory 中整合車隊與配送路線的功能模組。功能包含：
- 建立配送批次時指定車輛（Vehicle），系統自動計算重量/體積使用率
- 倉庫儲位可設定為「Dock Location（碼頭）」，代表裝卸點
- 整合 Google Maps 顯示批次配送路線
- 支援列印批次路線單

啟用條件：
1. Fleet App（車隊管理）已安裝且已建立車輛資料
2. Inventory → Configuration → Settings → Dispatch Management System 已啟用
3. 倉庫儲位需標示 Is a Dock Location

（參考 INV25）

### Q20：如何在 Odoo 中追蹤某批次商品的完整流向（從廠商到客戶）？

**A：** 兩種方式：
1. **從批號/序號查詢**：
   - Inventory → Products → Lots/Serial Numbers
   - 點選特定批號 → 點擊 **Traceability Smart Button**
   - 顯示完整路徑：廠商 → Receipt → Stock → Delivery → 客戶

2. **從移轉單查詢**：
   - 開啟任何 Receipt 或 Delivery → Traceability Smart Button
   - 顯示此單據中所有批號的移動路徑

追蹤報告可協助：
- 產品召回（快速找出同批號的所有銷售訂單）
- 品質問題調查（追查哪批廠商原料有問題）
- 法規要求的溯源文件

（參考 INV13、INV14）

## 四、易混淆概念類

### Q21：Physical Inventory（實地盤點）和 Inventory Adjustment（庫存調整）是一樣的嗎？

**A：** 兩者密切相關但有區別：
- **Physical Inventory** 是操作界面，顯示所有可盤點的產品與在手數量，讓倉庫人員在此填入實際清點數量。
- **Inventory Adjustment** 是系統動作，當點擊 Apply Quantities 後，系統依差異量建立一筆移轉記錄（從 Virtual/Inventory Adjustment Location 移入或移出）以更新帳面庫存。

實際上，在 Physical Inventory 頁面操作後，「Apply」的動作就是在執行 Inventory Adjustment。（參考 INV10）

---

### Q22：為什麼 Validate 後庫存沒有更新？

**A：** 常見原因及解決方式：
1. **產品未設定 Track Inventory**：Product Type = Goods 但未勾選 Track Inventory → 庫存不會被追蹤，不會顯示於 Physical Inventory。
2. **產品 Type = Consumable**：消耗品不追蹤庫存。
3. **儲位設為 Virtual 位置**：移至 Virtual Location 不計入實體庫存。
4. **頁面未重新整理**：在 Physical Inventory 中需重新整理頁面才顯示最新數量。

確認方式：Products → 點擊產品 → Inventory Tab → 查看 On Hand Quantity，或按 F5 重整 Physical Inventory 頁面。（參考 INV01）

### Q23：Scrap（報廢）和 Inventory Loss 有什麼關聯？

**A：**
- **Scrap**（報廢）是一個操作動作（Operations → Scrap），將損壞/過期商品從可用庫存中移除。
- **Inventory Loss Location** 是 Odoo 系統中用於「消失的庫存」的虛擬儲位，Scrap 目標位置（Scrap Location）通常設定為 Inventory Loss 類型。
- 報廢動作的帳務：商品成本移至 Loss Account（損失科目），反映於損益表（P&L）的費用項目。

因此：Scrap（動作）→ 移至 Scrap Location（Inventory Loss 類型儲位）→ 產生會計分錄。（參考 INV11）
