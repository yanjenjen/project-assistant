# Odoo Website & eCommerce 模組 - 內控點與風險

> 模組：Website + eCommerce
> 版本標示：Odoo（依影片介面推測，待確認）
> 學習日期：2026-07-30
> 狀態：草稿
> 資料來源：26 支官方教學影片（ECM01–ECM26）

## 一、存取權限設定

### 1-1 網站後台存取控制

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| Website Editor 存取 | 可進入編輯模式的使用者即可修改所有網站頁面內容，包含發布/下架商品 | 高 |
| eCommerce 後台存取 | eCommerce → Products/Orders/Categories 等後台功能，應依角色限制 | 高 |
| Configuration → Settings | 包含付款、配送、帳號政策等關鍵設定，應限制為系統管理員 | 高 |
| 開發者模式 | 啟用後可存取 URL 重定向、robots.txt 等技術設定，應嚴格限制 | 中 |

**建議措施：**
- 在 Odoo Settings → Users & Companies → Users 設定使用者角色，區分「Website/eCommerce 編輯者」與「Website/eCommerce 管理者」的存取範圍
- 非必要人員不應具備 Website Settings 的修改權限

### 1-2 顧客 Portal 存取管理

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| Portal Access 授予 | 僅特定顧客（如 B2B）獲得 Portal 存取時，需人工審核後才授予，不可自動開放 | 中 |
| 帳號建立政策 | 設定為 Optional 時，訪客可在購買後自行建立帳號（可能有垃圾帳號風險）；設定為 Mandatory 時，未授權使用者無法購物 | 中 |
| Portal Access 撤銷 | 顧客關係終止或 B2B 客戶退出時，需主動撤銷 Portal 存取 | 中 |

**建議措施：**
- 定期審核已授予 Portal 存取的顧客清單
- B2B 專屬網站建議設定為 Mandatory 帳號政策，並僅授予核准的顧客

## 二、付款安全控制

### 2-1 付款供應商設定控制

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| 測試模式 vs. 正式模式 | 若供應商設定留在 Test Mode，訂單付款不會實際扣款，可能造成假訂單正常出貨 | 高 |
| API 憑證保管 | Payment Provider 的 API Key/Secret 具有金融交易授權，洩露可能導致詐騙 | 高 |
| 手動捕獲金額設定 | 啟用「Capture Amount Manually」時，已授權的款項需人工確認才真正扣款；若流程不清楚可能造成訂單未扣款即出貨 | 高 |
| 最小/最大訂單金額限制 | 用於限制特定付款方式（如信用卡只接受 €100 以上）的濫用，應根據業務邏輯正確設定 | 中 |

**建議措施：**
- 上線前必須確認付款供應商已從 Test Mode 切換為 Enabled
- API 憑證不得寫入任何文件、Email 或共用平台；僅在 Odoo 後台設定
- 啟用「手動捕獲」時，須建立明確的 SOP：何時捕獲、誰負責操作
- 定期審查已啟用的付款供應商，停用不再使用的供應商

### 2-2 退款控制

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| 退貨審核 | Odoo 的退貨按鈕操作後即直接驗收退貨商品，無強制審核流程 | 中 |
| 退款授權 | 退款信用憑單在 Accounting 模組中操作，需具備 Accounting 權限才可執行 | 中 |
| 換貨管理 | 以相同商品換貨時，若庫存不足仍會建立退貨，但不會自動追蹤換貨出貨狀態 | 低 |

**建議措施：**
- 退款流程需在 Accounting 模組中由會計人員確認，不可由 eCommerce 人員單方面執行退款
- 建立退貨授權流程（如超過一定金額需主管審批）

## 三、庫存連動風險

### 3-1 超賣風險

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| 繼續銷售設定 | eCommerce 分頁「Continue Selling When Out of Stock」啟用時，庫存歸零仍可下單，可能造成超賣 | 高 |
| 變體庫存追蹤 | 若商品有多個變體（顏色×尺寸），每個變體的庫存獨立追蹤；若未正確設定各變體庫存，可能顯示有貨但實際缺貨 | 高 |
| 批次匯入庫存 | 批次匯入商品時，若未同步設定庫存，所有商品初始庫存為 0 | 中 |

**建議措施：**
- 一般消費品建議關閉「Continue Selling When Out of Stock」，改顯示缺貨訊息
- 對於允許超賣的商品（如預購），需特別標注並建立補貨通知流程
- 批次匯入商品後，需立即進行庫存盤點並更新數量

### 3-2 補貨規則風險

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| 補貨規則門檻設定 | Min Qty 設定過高可能頻繁觸發補貨；設定過低可能在銷售高峰期缺貨 | 中 |
| 補貨規則的供應商設定 | 待補資料（影片未詳述，需確認補貨規則是否能自動對應指定供應商） | 需確認 |

### 3-3 Click and Collect 庫存控制

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| 取貨倉庫庫存 | Click & Collect 依賴 Inventory 中的倉庫庫存，需確保取貨地點庫存正確 | 中 |
| 多倉庫取貨 | 顧客選擇特定取貨地點後，Odoo 需正確從該倉庫扣除庫存 | 中 |

## 四、定價管理風險

### 4-1 價格表（Price List）錯誤設定風險

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| Selectable Price List 外洩 | 設定為 Selectable 的價格表（如批發價）若被一般消費者選擇，可能以批發價購物 | 高 |
| 促銷代碼外洩 | Promo Code 若被廣泛分享，可能造成超出預期的折扣使用 | 中 |
| 比較價格設定錯誤 | Compared to Price 低於 Sales Price 時，刪除線不會顯示，但設定本身不會報錯 | 低 |
| 免費配送門檻設定 | 配送方式中的免費配送門檻若設定錯誤（如設為 0），所有訂單均免運費 | 高 |
| 多幣別匯率 | Odoo 依設定的匯率轉換幣別；若匯率長期未更新，外幣定價可能不準確 | 中 |

**建議措施：**
- 批發/特殊客戶的 Price List 不應設為「Selectable」，改用「Country Groups」或由業務人員手動指派
- 促銷代碼啟動前確認有效期限與使用次數上限
- 定期審查已啟用的 Price Lists，下架不再使用的促銷活動
- 外幣匯率應定期更新（至少每月一次）

### 4-2 商品定價異常

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| 變體定價不一致 | 屬性的「Default Extra Price」套用至所有含此屬性的商品，若僅想調整特定商品的特定變體，需在商品頁的 Variants 中個別設定，否則會影響所有商品 | 高 |
| 稅率設定 | 若商品稅率設定錯誤，網站顯示價格（含稅）與實際扣稅金額可能不符 | 中 |
| 稅含/稅外顯示 | 設定「Show Tax Inclusive Prices」時，顯示價格已含稅；若未設定可能造成顧客認知誤差 | 中 |

## 五、SEO 與內容管理風險

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| H1 多重 | 每頁超過一個 H1 會負面影響 SEO 排名 | 低 |
| URL 更改未建立重定向 | 直接修改頁面 URL 而未建立重定向，會導致舊 URL 404 錯誤，失去原有 SEO 排名 | 中 |
| AI 生成內容未審核 | Blog 文章或商品描述使用 AI 生成後直接發布，可能包含不準確或不適當的內容 | 中 |
| 圖片版權 | 使用非 Unsplash 圖庫的外部圖片，需確認版權授權 | 中 |
| Meta Description 重複 | 不同頁面使用相同 Meta Description，降低 SEO 效果 | 低 |

**建議措施：**
- 建立內容審核流程：AI 生成內容需經人工確認後才發布
- 修改 URL 前必須先建立 301 重定向（開發者模式下操作）
- 所有使用的外部圖片需記錄來源與授權類型

## 六、多網站管理風險

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| 設定影響範圍混淆 | 多網站時，前台修改只影響當前網站；但後台記錄（如商品）預設跨網站共用，可能造成誤以為某個修改只影響一個網站 | 中 |
| 產品/分類跨網站共用 | 商品若未設定「Website」欄位，所有網站均可看到此商品；若有 A/B 兩個品牌網站，需確保各自的商品正確隔離 | 高 |
| Contact Form 路由 | 多網站時 Contact Form 的 Email 收件人需分別設定，否則 A 網站的詢問可能發到 B 網站的信箱 | 中 |
| Price List 多網站限制 | 未在 Price List 的 e-Commerce 分頁設定「Website」時，所有網站均適用此價格表 | 中 |

**建議措施：**
- 多網站環境下，每個商品在 Sales 分頁的「Website」欄位需明確指定所屬網站
- 多網站時所有 Contact Form 需個別確認 Email 路由正確性
- 建立多網站測試 Checklist，在每次網站修改後確認另一網站未受影響

## 七、忠誠計劃與促銷管理風險

| 控制點 | 說明 | 風險等級 |
|--------|------|---------|
| 積點累積無上限 | 若未設定每位顧客的使用次數上限，高消費客戶可累積大量積點，一次兌換造成大額折扣 | 中 |
| 禮品卡代碼管理 | 禮品卡代碼一旦生成即可使用，若代碼外洩或被猜中，可能被非目標顧客使用 | 中 |
| eWallet 帳戶安全 | eWallet 儲存虛擬金額，若顧客帳號被盜用，eWallet 餘額可能被消耗 | 高 |
| 忠誠計劃跨 POS 共用 | 若 Point of Sale 也啟用同一忠誠計劃，實體門市積點與線上積點共用，需確認政策一致 | 低 |

**建議措施：**
- 設定忠誠計劃時應設定「Limit Usage」（每位顧客使用次數上限）
- 禮品卡生成數量應根據實際銷售計劃設定，避免生成過多未使用代碼
- 鼓勵顧客設定強密碼並啟用兩步驟驗證（若平台支援）
