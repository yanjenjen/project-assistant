## 內控點清單

### IC-01｜Settings 設定頁面不自動儲存

| 項目 | 說明 |
|------|------|
| 類型 | 系統例外控制 |
| 風險 | 使用者在 Settings 頁面修改後忘記點儲存，變更遺失 |
| 控制機制 | 無自動儲存，需手動點 Save 按鈕 |
| 顧問提醒 | **所有模組 Demo 與教育訓練必提**，此為常見客戶錯誤 |

---

### IC-02｜雙因素驗證 2FA 設定

| 項目 | 說明 |
|------|------|
| 類型 | 權限控制 / 資安控制 |
| 位置 | 頭像 → 偏好設定 Preferences → 帳號安全 Account Security → 雙因素驗證 2FA |
| 風險 | 未啟用 2FA 的帳號若密碼外洩，直接被入侵 |
| 建議 | 導入時建議管理員帳號強制啟用 2FA |

---

### IC-03｜多公司資料隔離 Multi-company Data Isolation

| 項目 | 說明 |
|------|------|
| 類型 | 資料隔離控制 |
| 風險 | 切換公司時若操作未完成，資料可能寫入錯誤公司 |
| 控制機制 | 頂部工具列的多公司切換 Multi-company Toggle 明顯標示當前公司 |
| 建議 | 多公司設定需由 IT 或顧問統一規劃，不建議讓一般使用者自行切換 |

---

### IC-04｜Studio 模組自訂權限 Studio Access Control

| 項目 | 說明 |
|------|------|
| 類型 | 權限控制 |
| 風險 | 未授權使用者進入 Studio 修改 App 欄位或介面 |
| 控制機制 | Studio 功能需要 Odoo Studio 授權，且需設定使用者存取權限 |
| 建議 | 僅開放系統管理員或顧問帳號使用 Studio |

---

### IC-05｜Preferences 頁籤可見性與使用者角色

| 項目 | 說明 |
|------|------|
| 類型 | 系統行為說明 |
| 說明 | 偏好設定 Preferences 的頁籤數量依安裝模組而異；一般使用者若無管理員權限，只看到基本頁籤 |
| 風險 | 使用者誤以為功能不存在（實際是沒有權限或未安裝） |

## Using Odoo 章節新增內控點（2026-07-15）

### IC-06｜日曆參與者 ≠ 正式邀請

| 項目 | 說明 |
|------|------|
| 類型 | 系統行為容易被誤解的操作 |
| 風險 | 使用者將他人加入「查看行程」，誤以為已正式邀請對方，導致對方未收到會議通知 |
| 控制機制 | 必須在「更多選項 More Options」中的參與者欄位正式加入，才會出現在對方行程 |
| 顧問提醒 | **教育訓練必提**，此為日曆最常見的使用錯誤 |

---

### IC-07｜罐頭回應授權群組控制

| 項目 | 說明 |
|------|------|
| 類型 | 權限控制 |
| 說明 | 罐頭回應預設僅建立者可用；即使管理員也必須在授權群組內才能使用 |
| 風險 | 管理員建立回應後，其他成員無法使用 |
| 建議 | 建立後立即設定授權群組，避免孤立回應 |

---

### IC-08｜聯絡人刪除限制

| 項目 | 說明 |
|------|------|
| 類型 | 系統控制 |
| 說明 | 已被其他 App（Sales/CRM/Accounting 等）使用的聯絡人無法直接刪除 |
| 控制機制 | 系統彈出警告，要求改用封存 Archive |
| 顧問提醒 | 清理資料庫時需注意，封存 ≠ 刪除，不佔用 licence 但資料仍存在 |

---

### IC-09｜匯入資料前先測試

| 項目 | 說明 |
|------|------|
| 類型 | 操作內控 |
| 說明 | Odoo 提供「測試 Test」功能，先驗證欄位對應與格式再實際匯入 |
| 風險 | 未測試直接匯入，欄位對應錯誤導致大量資料寫入錯誤欄位，難以復原 |
| 建議 | 任何批次匯入前必須先執行 Test，確認藍色成功訊息後再 Import |

---

### IC-10｜群組存取權限設計原則

| 項目 | 說明 |
|------|------|
| 類型 | 權限架構控制 |
| 說明 | 建議使用群組管理權限，而非對個別使用者設定 |
| 原因 | 人員異動時群組設定自動沿用，減少漏設或超設的風險 |
| 建議 | 導入初期與客戶確認各角色的 CRUD 需求，再建立對應群組 |

---

### IC-11｜Log Note vs. Send Message 的區別

| 項目 | 說明 |
|------|------|
| 類型 | 資料可見性控制 |
| 說明 | Send Message = 外部郵件（客戶可見）；Log Note = 內部備註（僅追蹤者可見）|
| 風險 | 誤用 Send Message 發送內部討論給客戶 |
| 顧問提醒 | 教育訓練必提此區別，尤其業務/客服人員 |

## Odoo Discuss 章節新增內控點（2026-07-15）

### IC-12｜WhatsApp 模板必須通過 Meta 審核才能使用

| 項目 | 說明 |
|------|------|
| 類型 | 外部平台依賴控制 |
| 說明 | WhatsApp 模板需提交 Meta 審核，審核時間數小時至 1 天，期間無法使用該模板 |
| 風險 | 客戶上線日緊迫時，若未提前送審，無法即時使用 WhatsApp 功能 |
| 建議 | 導入計畫中，WhatsApp 模板審核需提前 2-3 個工作日提交，不可等到上線前才送 |

---

### IC-13｜WhatsApp 15 天未互動通知規則

| 項目 | 說明 |
|------|------|
| 類型 | 通知設計控制 |
| 說明 | 若某客戶 15 天內未有模板訊息往來，下次客戶回覆時，Control 欄位中所有使用者都會收到通知（而非只通知最後發送者） |
| 風險 | 管理員收到大量通知，若未設定好 Control 欄位，造成通知混亂 |
| 建議 | WhatsApp 設定初期，Control 欄位明確指定負責人，不要讓所有人都在清單內 |

---

### IC-14｜Discuss 頻道授權群組留空 = 外部人員可加入

| 項目 | 說明 |
|------|------|
| 類型 | 資料可見性控制 |
| 說明 | 頻道隱私設定 → Authorized Group 若留空，任何持有邀請連結的人（含外部人員）均可加入 |
| 風險 | 誤將機密頻道的連結傳出，外部人員可直接加入查看對話 |
| 建議 | 除非刻意設計外部協作頻道，否則 Authorized Group 一律設定為 Internal Users 或特定群組 |

---

### IC-15｜WhatsApp 訊息類別需符合 Meta 規範

| 項目 | 說明 |
|------|------|
| 類型 | 合規控制 |
| 說明 | WhatsApp 模板類別分 Marketing / Authentication / Utility，錯誤分類可能導致審核被拒或被 Meta 封號 |
| 風險 | 將行銷內容誤標為 Utility 試圖規避審查，Meta 可能拒絕或停用帳號 |
| 建議 | 顧問協助客戶設定模板時，需確認內容符合選擇的類別；涉及行銷性質的訊息請勿使用 Utility 類別 |

### IC-16｜Sign 模板存放位置易混淆

| 項目 | 說明 |
|------|------|
| 類型 | 操作風險 |
| 說明 | 已設計好的電子簽署模板存放於「Sign App → 模板 Templates」，**不在** Documents App 中 |
| 風險 | 使用者在 Documents App 找不到模板，誤以為模板消失而重複建立 |
| 建議 | 上線教育訓練需特別說明兩個 App 的分工：Documents 存放已簽署成品，Sign 存放可重複使用的模板 |

---

### IC-17｜分析帳戶需先在 Accounting 啟用才可使用

| 項目 | 說明 |
|------|------|
| 類型 | 設定前提 |
| 說明 | Analytic Accounting（分析會計）功能需在 Accounting → Configuration → Settings 中手動啟用，啟用後採購單明細才出現「分析分配 Analytic Distribution」欄位 |
| 風險 | 未啟用時顧問無法示範採購 ↔ 銷售專案成本聯結，客戶可能誤以為 Odoo 缺少此功能 |
| 建議 | 服務業/建設業/專案型企業導入時，Analytic Accounting 為必備設定；Demo 前請確認已開啟 |

---

### IC-18｜MTO 路線預設封存，需手動解除

| 項目 | 說明 |
|------|------|
| 類型 | 系統預設風險 |
| 說明 | 「按訂單補貨 Replenish on Order (MTO)」路線在 Odoo 中預設為封存 Archived 狀態，不會出現在產品的路線選項中 |
| 風險 | 顧問協助設定製造流程時若未發現此問題，MTO 功能無法使用，影響 Demo 完整性 |
| 建議 | 前往 Inventory → Configuration → Routes → 篩選 Archived → 找到 MTO → 解除封存 Unarchive |

---

### IC-19｜時程表工時需審核才計入已交付數量

| 項目 | 說明 |
|------|------|
| 類型 | 流程控制 |
| 說明 | 服務型產品使用「時程表計費 Invoicing Policy = Timesheets」時，專案任務的工時紀錄需通過**時程表審核**，才會反映在銷售訂單的「已交付 Delivered」數量欄中 |
| 風險 | 時程表未送審或未批准 → 銷售訂單顯示 0 已交付 → 無法開立客戶發票 → 影響收款時程 |
| 建議 | 訪談時確認企業是否需要時程表審核層（主管審核）；若不需要，可在 Project Settings 中關閉強制審核 |

---

### IC-20｜文件自動化規則的觸發時機需重新整理頁面才生效

| 項目 | 說明 |
|------|------|
| 類型 | 使用者體驗 |
| 說明 | Documents App 的自動化規則（如加標籤觸發移動資料夾）在觸發後需手動重新整理 Refresh 頁面，才能看到文件已移動的結果 |
| 風險 | 使用者看到文件沒有立即移動，誤以為自動化失效，重複操作或誤報問題 |
| 建議 | 上線教育訓練說明自動化觸發後需重整頁面；或在操作文件/FAQ 中標注此行為 |

## Getting Started 核心操作內控點（2026-07-15）

> 來源：Create an Odoo Database + Multi-Company Basics + Multi-Company Transactions

### IC-21｜資料庫啟用期限：3 小時內必須點擊啟用連結

**風險**：建立資料庫後若未在 3 小時內點擊啟用信中的連結，**所有資料自動清除且無法復原**。
**控制點**：建立後立即查收 Email → 點擊啟用連結。Demo 環境亦需注意。
**顧問建議**：客戶 Go-Live 建立正式資料庫當下，立即確認啟用。

---

### IC-22｜Country 設定不可更改，直接決定科目表

**風險**：資料庫建立時若選錯 Country，Accounting App 安裝後的科目表將以錯誤國家為基礎，無法更換。
**控制點**：建立前務必確認公司所在國家 → 尤其跨國企業每家子公司需分別確認。
**顧問建議**：訪談時明確詢問「公司登記地在哪裡？主要幣別？是否有多國子公司？」

---

### IC-23｜Currency 幣別一旦有第一筆交易後永久鎖定

**風險**：若誤設幣別後已進行任何交易（發票/帳單/庫存移動），幣別無法修改，需重建資料庫。
**控制點**：建立公司 / 子公司後立即確認幣別設定，在任何交易前先驗證。
**顧問建議**：多公司場景特別注意，每個子公司需分別確認幣別。

---

### IC-24｜公司建立後不可刪除

**風險**：誤建公司（如測試用）無法刪除，只能封存，會永遠佔用系統資源與使用者選單。
**控制點**：建立任何公司前 300% 確認需求。測試用子公司應在沙盒環境建立。
**顧問建議**：GA 之前，正式資料庫只建立確定需要的公司。

---

### IC-25｜Demo 資料不可在正式資料庫使用

**風險**：在正式資料庫 Load Demo Data，**原有所有資料將被覆蓋，無法復原**。
**控制點**：Developer Mode 下才看得到此按鈕；正式環境不應開啟 Developer Mode。
**顧問建議**：教育訓練一律使用獨立訓練資料庫，嚴禁在客戶正式環境操作。

---

### IC-26｜財務本地化套件設定後若已有自訂科目表將全部清除

**風險**：已設定自訂 Chart of Accounts 後，若再次修改 Fiscal Localization Package，系統將清除所有自訂科目。
**控制點**：導入順序必須是：先確定國家 → 先選套件 → 再建科目 → 再建日記帳。
**顧問建議**：Accounting 導入前，先確認客戶所在地的本地化套件，不可事後補設。

---

### IC-27｜跨公司交易必須從商業單據（PO/SO）開始，不可從財務單據反向建立

**風險**：若從發票/帳單開始建立，系統無法自動反向生成採購訂單/銷售訂單，跨公司流程中斷。
**控制點**：跨公司交易標準流程 = 先建 PO（買方）→ 自動產生 SO（賣方）→ 出貨 → 開票 → 自動產生帳單。
**顧問建議**：在跨公司 UAT 時明確列出操作順序，不可讓使用者從 Accounting 頁面開始。

---

### IC-28｜Access Rights（存取權）與 Record Rules（記錄規則）是兩層不同的權限機制

| 項目 | 說明 |
|------|------|
| 類型 | 權限架構控制 |
| 說明 | Access Rights 決定「能不能操作某個模型」（模型層級 CRUD）；Record Rules 決定「能操作模型裡的哪些具體記錄」（記錄層級 domain 篩選）。兩者是疊加關係，缺一不可 |
| 風險 | 顧問若只在 Groups 表單的「存取權限」頁籤設定 CRUD，卻忽略 Record Rules，容易誤以為「權限已設好」，實際上該群組仍套用系統預設或未設定的記錄規則，可能造成客戶資料外洩，或員工看不到自己該看的資料（如業務看不到自己名下的訂單） |
| 建議 | 導入時針對「業務只能看自己客戶/訂單」等常見需求，務必在開發者模式下到 Settings → Technical → Security → Record Rules 用「模型」篩選核對，不能只看 Groups 表單的 CRUD 勾選就結案 |
| 參考範例 | Sales 模組原生已有此設計：「銷售/使用者」群組套用 Personal Orders 規則（`user_id = 自己 或 未指派`），「銷售/管理員」群組套用 All Orders 規則（全部可見），可作為向客戶說明的標準範例 |

---

### IC-29｜聯絡人標籤（Tags）不具備權限管控功能，僅供分類與篩選

| 項目 | 說明 |
|------|------|
| 類型 | 功能誤解風險 |
| 說明 | 聯絡人標籤（res.partner.category）是純粹的分類/顏色標記工具，用於清單篩選、群組統計、行銷區隔；標籤本身**不會**限制「誰能看到這筆聯絡人」 |
| 風險 | 客戶常誤以為「幫聯絡人加標籤 = 設定存取權限」，例如想用標籤做到「業務 A 只能看到貼有〔A區〕標籤的客戶」，但 Odoo 原生標籤不驅動任何 Record Rule，這個需求做不到，除非另外客製一條在 domain 中引用 category_id 的記錄規則 |
| 建議 | 訪談時務必區分「分類需求」（用標籤即可）與「權限隔離需求」（要用 Record Rules，通常搭配業務員/公司/部門欄位而非標籤），避免客戶上線後才發現標籤沒有預期的管控效果 |
