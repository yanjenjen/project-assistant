# 新客戶 Odoo ERP 環境快速建置 QA SOP

## 核心精神

新客戶通常不知道自己需要準備什麼資料，才能把 ERP 架起來。顧問的責任是「主動用結構化方式引導客戶盤點」，而不是被動等客戶講需求。

本技能把 [[Odoo知識庫]] 各模組 `04_內控點與風險.md` 中累積的「顧問訪談問題」收斂成一份跨模組執行指南，並要求每個功能都回答「依產業，為什麼要建置這個功能」（見 Getting Started SOP-42/43 的寫法），而不是只列技術步驟。

## 何時啟用 (When to Activate)

- 新客戶第一次訪談前，需要準備要問的問題清單
- 規劃 Demo 環境或正式環境的建置順序
- 判斷「客戶提的這個需求」該調查什麼基礎資料、屬於哪個模組
- 盤點模組間功能關聯性，避免導入順序出錯（例如還沒確認多公司架構就先建科目表）
- 客戶說「我想要 XX 功能」但講不清楚，需要用產業情境反推真正需求

## 使用流程

0. **建立專案資料夾**：新客戶專案一律複製 `00_專案資料夾範本/`（100/200/300 結構）整份，改名為客戶名稱（如 `建大工業_經銷商平台專案/`），放在 `艾創點數位-ERP顧問/` 外層，與 `顧問Cowork/` 平行。這是公司層級的歸檔主結構，本技能產出的每一項東西最終都要歸位到這裡（見下方「表三」）。
1. **確認知識庫完成度**：讀 `Odoo知識庫/00_學習進度總覽.md`，看各模組狀態（✅已完成 / 📖知道 / 🔲未開始）。未完成模組的訪談清單可能不完整，如果客戶需求落在這些模組，要明確告知使用者「這塊我們知識庫還沒補齊，訪談內容可能不夠細」，不要假裝已知。
2. **第一輪：全案基礎資料**（見下方表一）——任何模組訪談之前都要先問過一輪，這些答案會決定後面每個模組怎麼設計。
3. **第二輪：依業務循環對模組**（見下方表二）——依客戶會用到的循環（銷售/採購/庫存/財務/製造），逐一過一遍「建置前必備基礎資料」與「與其他模組的關聯性」。
4. **撈訪談清單細節**：每個模組完整的顧問訪談問題清單，維護在對應模組的 `Odoo知識庫/<模組>/04_內控點與風險.md` 檔案最下方，本技能只放摘要索引，避免兩份文件內容打架、其中一份忘記更新。
5. **產出兩種版本，並歸檔到對的位置**（見下方表三）：
   - **內部顧問版**：含系統設定細節、欄位/模型技術名稱，供顧問自己核對用。
   - **客戶交付版**：翻成客戶聽得懂的一句話（例如「Access Rights vs Record Rules」→「業務打開系統時，你希望他看到所有人的訂單，還是只看到自己的？」），不要直接把技術名詞丟給客戶。

## 表一｜全案啟動基礎資料（任何模組之前必問）

| 主題 | 要問客戶的問題（一句話版） | 決定了什麼 | 詳見 |
|------|-------------------------|-----------|------|
| 公司架構 | 公司有幾個法律實體/統一編號？彼此業務往來嗎？ | Multi-Company vs Branch vs Access Rights 怎麼選 | Getting Started Q29 |
| 幣別/會計本地化 | 主要交易幣別？公司登記地在哪？ | Fiscal Localization Package（事後不可改）、Currency（第一筆交易後鎖定） | Getting Started IC-22/23 |
| 使用者與權限 | 有多少使用者？業務打開系統要看到所有人的資料，還是只看自己的？ | Groups 設計、Access Rights vs Record Rules | Getting Started SOP-18/43、IC-28 |
| 聯絡人分類需求 | 客戶/廠商目前怎麼分類（現有 Excel 欄位）？是分類需求還是「不同人看不同客戶」的權限需求？ | 聯絡人標籤設計 vs 是否要客製 Record Rule | Getting Started SOP-42、IC-29 |
| 資料遷移 | 舊系統/Excel 資料格式長怎樣？ | 匯入 SOP、欄位對應規劃 | Getting Started SOP-13 |
| 上線時程 | 預計上線日期？教育訓練要不要獨立 Demo 環境？ | 專案排程、Demo 資料需求 | Getting Started IC-25 |

| 模組 | 業務循環定位 | 建置前必備基礎資料 | 與其他模組關聯性 | 知識庫狀態 |
|------|------------|-------------------|-----------------|-----------|
| Getting Started | 系統基礎操作/組織架構 | 見表一 | 所有模組的地基（權限、聯絡人、多公司） | ✅ 已完成 |
| CRM | 客戶開發 → 商機 → 報價 | 銷售團隊/業務分工、商機階段定義、Lead 來源（網站/活動/手動/信箱外掛） | Won 商機 → 直接轉 Sales 報價；共用 Contacts | ✅ 已完成 |
| Sales | 報價 → 訂單 → 出貨 → 發票 → 收款 | 產品目錄 + 發票政策（依訂購/依交付/服務型）、價格表、報價範本、稅別 | 出貨連動 Inventory；發票連動 Accounting | ✅ 已完成 |

| Accounting | 發票 → 付款 → 對帳 → 結帳 | 科目表、日記帳、稅別、銀行帳戶 | 承接 Sales/Purchase 產生的發票/帳單 | 🔲 未開始，訪談清單待補 |
| Manufacturing | BOM → 工單 → 領料 → 入庫 | 物料清單 BOM、工作中心、途程 | 承接 Purchase 原料，產出供 Sales/Inventory | 🔲 未開始，訪談清單待補 |

## 模組間功能關聯性地圖

```
Contacts（聯絡人＋標籤）──── 所有模組共用的基礎資料
Products（產品/服務）────── Sales / Purchase / Inventory / Manufacturing 共用基礎
Access Rights + Record Rules ── 橫跨所有模組的權限層，不是單一模組設定

CRM (商機 Won)
   → Sales (報價 → 訂單)
        → Inventory (出貨)
        → Accounting (發票)
   Purchase (詢價 → PO)
        → Inventory (收貨)
        → Accounting (帳單)
   Manufacturing (若有生產)
        Purchase(原料) → Manufacturing(BOM/工單) → Inventory(入庫) → Sales(可售)
```

**判斷原則**：客戶提出任何新需求，先問「這個需求主要卡在哪個循環？」，再往前推「這個循環的建置前必備資料，客戶給了嗎？」——沒給的話,先蒐集資料,不要跳過去直接開始設定。

## 表三｜產出物歸檔位置（對應 `00_專案資料夾範本` 100/200/300 結構）

本技能問出來、整理出來的每一項東西，最終都要落在客戶專案資料夾（複製自 `00_專案資料夾範本/`）對應位置，不要散落在 Odoo知識庫 或聊天記錄裡：

| 本技能產出物 | 歸檔位置 | 說明 |
|------------|---------|------|
| 表一/表二訪談的原始回答、客戶提供的截圖/文件/系統架構圖 | `200_專案資料/220_客戶提供資料` | 客戶給的原始素材 |
| 訪談會議紀錄（內部討論，非給客戶看） | `200_專案資料/210_內部會議記錄` | 顧問內部整理的訪談逐字稿/重點摘要 |
| 內部顧問版檢查清單、技術設定草稿、Groups/Record Rules 設計草稿 | `200_專案資料/230_內部專案檔案` | 不交付客戶的技術文件與草稿 |
| 客戶交付版資料準備清單、正式規格確認書（SA/SD） | `100_專案執行與交付/110_規格確認書` | 需客戶回簽的正式文件 |
| 客戶連線資訊（VPN/遠端桌面/DB/系統後台） | `300_連線方式` | 專案連線相關 |
| 驗收相關文件 | `100_專案執行與交付/120_驗收單` | 客戶回簽驗收單 |
| 若走顧問輔導時數計價 | `100_專案執行與交付/130_階段報告&輔導備忘` | 依輔導時數計價之正式交付文件 |

若專案同時有 `顧問Cowork` AI 三員工協作，草稿先留在 `顧問Cowork/91_跨員工協作區/[企業代號]_[日期]_[任務名稱]/`，AI 產出確認版可暫存 `顧問Cowork/90_正式交付成果/`；兩者都不取代上表的 100/200/300 正式歸檔，草稿確認後仍要依性質歸位。詳細治理規則見 `顧問Cowork/00_共用規則與知識庫/01_工作區規則/專案資料夾結構與歸檔規則.md`。
