# 產品分類與屬性/變體重建——A方案調整計畫SOP

> 建立日期：2026-07-27
> 背景：階段三之二（內胎與組合商品）用「40個各自獨立的商品＋BoM Kit」做完後，
> 使用者指出兩個根本問題：(1) 商品完全沒有「類別」(2) 組合商品的建立方式本身
> 架構有誤，應該先建好分類/屬性體系，再依體系建產品與配對，而不是先把內胎/
> 組合當一般商品堆上去。本文件記錄重新設計後的方案（稱「A方案修正版」）與
> 具體執行步驟，取代原本 `Odoo資料匯入SOP.md` 階段三之二第3-4步的做法。

---

## 一、問題發現（決策依據）

### 1. 產品類別欄位（categ_id）全部120筆都是空的
用API查證，不只是新增的80筆，連7/24已完成、驗收過的原始40筆外胎也一樣沒有
設定「類別」欄位。之前做的「10個標籤」是`product.tag`（標籤，無父子層級），
跟Odoo正規的`product.category`（產品分類，有父子層級）是兩個不同機制。

### 2. 原本的「5類代表性BOM分類」漏了「車種」這一層
逐一比對40筆外胎的品名，發現代號開頭「JR」的4筆（`205/55R16`／`185/65R15`／
`195/60R15`）是**標準轎車輪胎尺寸標示法**，不是自行車尺寸；其餘36筆
（JA/JB/JE/JI/JM開頭）才是自行車胎。原本的分類設計只想到自行車，
完全沒考慮到這批產品其實混了汽車胎，這是分類架構上的缺口。

### 3. 花紋(JSxxx)與尺寸有真實的交叉重複，可以支援屬性/變體模型
完整比對40筆外胎的「尺寸＋花紋代號＋顏色」後：
- 花紋代號共有 **30種**（JS100~JS390，間隔10）
- 其中 **10種花紋各出現2次**（配2種不同尺寸），其餘20種花紋各只出現1次
- **顏色(GY/BK)不是獨立變化的維度**——每個花紋代號的顏色是固定的，
  資料裡沒有出現「同花紋不同色」的組合，所以顏色比較像花紋本身附帶的
  特性，不適合當成會產生變體的獨立屬性
- **資料品質問題**：10種「花紋出現2次」裡，有4種其實是「尺寸＋花紋＋顏色」
  完全相同、只是內部參照代號不同的重複資料（JS150/JS170/JS180/JS190），
  是原始合成資料隨機產生時的巧合重複，不是人為造成

### 4. 配對邏輯的補充原則（使用者2026-07-27確認）
外胎+內胎能不能配成組合，必須同時滿足：
1. **同一種車種**（自行車／轎車，不可能自行車外胎配汽車內胎）
2. **同一種尺寸**
本次原始40筆的T/K系列是直接從對應外胎的代號與尺寸衍生出來的，所以車種與
尺寸本來就會一致；但這個原則要寫進文件，作為之後任何新增配對都要遵守的
規則，也是判斷「4組重複資料該合併」的依據——尺寸/車種/花紋/顏色完全相同
的兩筆，本來就該是同一個變體，不該產生兩組不同的組合商品。

## 二、最終決策

| 決策點 | 結論 |
|---|---|
| 產品分類 vs 標籤 | 改用有父子層級的「產品分類」(categ_id)，原本40筆外胎上的6個標籤**連定義一起刪除** |
| 分類樹頂層 | 新增「車種」這一層（自行車／轎車），修正原設計的缺口 |
| 屬性/變體範圍 | **全部重建**：把40筆獨立外胎商品，依「花紋」合併成30個產品範本，範本內用「尺寸」屬性產生變體 |
| 4組完全重複資料 | **合併為1個變體**，不人為竄改尺寸文字硬湊成兩個變體（那樣會製造假資料）|
| 內胎／組合商品 | 比照外胎的合併結果同步重建，最終筆數跟著外胎從40筆降到36筆 |
| BoM Kit | 40組全部依新的變體ID重新建立（舊的39組XML-RPC建的BoM會失效，需重建）|

**統計**：30個範本 → 6個範本有2個真實變體（JS100/110/120/130/140/160）＋
4個範本因重複合併只留1變體（JS150/170/180/190）＋20個範本天生只有1筆資料
（JS200~390，扣掉4個已列在前面的）＝ **合計36個變體**，對應36筆內胎、
36筆組合商品。

**誠實揭露**：屬性/變體機制在這批資料裡的實際效益有限——30個範本中只有
6個真的展示「同範本多尺寸變體」的行為，其餘24個範本各自只有1個變體
（技術上仍算「有屬性但只有一個值」，跟過去的獨立商品在使用體驗上差異不大）。
決定全部重建的理由是**架構正確性**（未來如果補真實花紋資料，多尺寸變體會
自然增加），而不是這輪就能看到很大的實際效益，先讓使用者知悉這個預期落差。

## 五、執行步驟（尚未執行，待下一輪session動手）

1. **刪除舊資料**：120筆商品（40外胎+40內胎+40組合）＋39組已建的BoM Kit
   全部刪除，改用下面全新的結構重建（不用逐筆改，砍掉重建比較乾淨，且
   報價/訂單階段都還沒開始，沒有交易參照，可安全刪除）
2. **建立9個product.category**（見第三節分類樹）
3. **移除原10個product.tag定義**（含指派關係，標籤定義本身也刪除）
4. **建立屬性「尺寸」**（product.attribute，逐一花紋範本各自的尺寸值當作
   attribute value；顏色不建屬性，寫進範本名稱/描述即可）
5. **建立30個外胎產品範本**，每個範本：
   - 名稱：花紋代號＋（如有2尺寸則不含尺寸，變體會自動帶；如只有1尺寸則
     可以把尺寸寫進名稱，比照原本命名習慣）
   - 類別：依原代號開頭（JR→轎車輪胎；JA/JI→公路/競賽胎or越野視花紋樣式；
     JB→入門代步胎；JM→越野/登山胎；JE→視情況歸類，需要跟使用者核對
     JA/JE/JI的5類歸屬細節，本文件先只確定「車種」大分類，5類子分類的
     逐筆歸屬要在執行時跟`集團產品主檔`原始的「產品系列」欄位比對，
     不能只憑代號開頭猜）
   - 屬性：尺寸（1或2個值）
6. **內胎、組合商品比照重建**（36筆各自），內部參照規則不變（T+外胎代號／
   K+外胎代號），但外胎代號改指向「保留下來」的那個代號（汰除的4個舊代號
   不再使用）
7. **重建36組BoM Kit**（元件=新變體的product.product ID，需重新查詢，
   舊的ID全部作廢）
8. **驗證**：抽查每個類別下的商品數量、抽查2-3組多變體範本、抽查4組合併案例
   確認沒有殘留舊代號
9. **更新文件**：本檔案的「執行狀態」表格、以及主文件`Odoo資料匯入SOP.md`
   階段三／三之二的狀態改回「重新設計中」並附註連結到本文件

  完全不受影響——這正是現在做這個重建的好時機，晚了報價單/訂單一旦
  引用了舊的產品代號，重建代價會更高
- **階段七（多公司）**：不受影響
