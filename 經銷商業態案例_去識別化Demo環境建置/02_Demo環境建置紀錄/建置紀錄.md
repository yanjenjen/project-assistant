### 判斷重點：真實「公司別」實際有7種，不只4種

盤點「建大公司定義」完整內容時發現，除了任務指示已知的4家生產基地
（代號1-4：建大臺灣/建泰深圳/建大昆山/建大越南），實際還有：
代號7「建大(天津)」、代號I「建大(印尼)」、**代號F「建豐(台灣)」**。

其中代號F（建豐台灣）尤其關鍵——真實「客戶主檔」46筆客戶資料中，
**40筆的公司別都是F**，只有6筆是代號1。也就是說，真實資料裡經銷商
客戶絕大多數是掛在「建豐(台灣)」這個前台貿易角色底下，而非直接掛在
4家生產基地。若照原指示只做4家虛構子公司，會讓客戶主檔失去可對應的
公司別、破壞跨表參照完整性。

**因此本次建置在使用者原定的4家虛構子公司之外，額外新增第5個虛構
角色「駿豐(臺灣)」（代號F、別名JF）**，對應真實的「建豐(台灣)」，
代表集團對外接單的前台貿易公司。這是本次建置過程中做出的判斷延伸，
特此在此標註供使用者確認；代號7(天津)、代號I(印尼)因為只出現在
「各公司代號檔」的訂單開頭碼描述文字中（非跨表關聯用的主檔外鍵），
因此只做文字置換（見下方三之2），未建立對應虛構子公司。

## 二、去識別化與縮小規模策略（分工作表說明）

### (A) 完全重新生成的主檔/交易資料（12個工作表）

依使用者確認的規模縮減策略，以下工作表**不做逐列去識別化**，而是
用固定亂數種子(seed=42)重新生成結構相同、內容純虛構、且跨表參照
一致的資料：

集團公司定義、業務員主檔(參考用)、客戶主檔、客戶指配地點檔、
集團產品主檔、各公司報價產品主檔、包裝部門、BC經銷商產品維護檔、
報價單頭、報價單身、集團訂單單頭(原建大訂單單頭)、集團訂單單身
(原建大訂單單身)。

跨表參照一致性重點：
- 客戶代號（JD10xx經銷商／JO10xx直接客戶）貫穿客戶主檔／客戶指配
  地點檔／報價單頭／訂單單頭
- 產品代號（J+類別碼+6位數字）貫穿集團產品主檔／各公司報價產品
  主檔／包裝部門／BC經銷商產品維護檔／報價單身／訂單單身
- 業務員帳號(sales01~05)貫穿業務員主檔與客戶主檔的salesUserId/salesMail
- 公司別代號(1/2/3/4/F)貫穿所有跨公司欄位，含訂單單身內的
  「生產公司別名/名稱」動態對應集團公司定義
- 訂單單身的quoteNo/quoteLineNo優先引用同一客戶實際存在的報價單
  及其明細項次（約85%訂單有對應報價來源），模擬真實下單多半源自
  報價的流程

### (B) 僅做示意、以單一合成訂單為基礎重建的說明性工作表（3個）

集團中介TABLE（原建大中介TABLE）、出貨單JSON示意、測試 ——
這三個工作表在真實資料中都只是格式/流程示意用的範例，不是完整
主檔。本次建置選擇「挑選一筆合成訂單資料，重新產生示意內容」，
而非逐列去識別化，因為：(1) 內容本來就是示意用途，不影響流程
理解；(2) 可確保示意範例中的訂單號/客戶代號/報價單號與其他工作表
的資料集是同一組虛構資料，內部前後一致。

## 三、零真實資料驗證

### 驗證方法

對輸出檔案 `經銷商業態_去識別化Demo資料集.xlsx` 的**全部17個工作表、
每一個儲存格（含工作表名稱本身）**，以 Python openpyxl 逐格掃描下列
目標字串：

```
建大, Kenda, KENDA, kenda, 建泰, 建豐
```

第一輪掃描發現「各公司代號檔」仍有6筆殘留"建豐"字樣（訂單開頭碼
說明文字，如"建豐出經銷商促銷訂單"），因初版置換清單只涵蓋
"建豐(台灣)"這個精確字串，未涵蓋單獨出現的"建豐"。修正置換清單、
加入"建豐"→"駿豐"的通用置換規則後，重新產生檔案並再次全表掃描。

### 驗證結果

```
TOTAL HITS ACROSS WORKBOOK: 0
```

17個工作表、全部儲存格，掃描結果為 **0 筆命中**，確認輸出檔案不含
任何真實建大工業相關字串（含公司名、品牌名、員工真實email網域）。
